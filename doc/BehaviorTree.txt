# Documentation — BehaviorTree.cpp Implementation

The BehaviorTree class is a small decision-making structure for a game character. On every tick it receives a context, which is simply a list of named integer facts about the current situation such as AtDoor equal to 0, Escudo equal to 22 and Energia equal to 100, and it answers with a single command string such as "Open" or "WalkToDoor". The character's own code then decides what that command means and carries it out. The idea is an alternative to a state machine: instead of writing transitions that inspect many variables inside nested if statements, you describe the decision once as a tree of tiny pieces, and the tree is asked the same question from the top every time. The tree is stateless. It remembers nothing between ticks, it does not keep track of a node that is "still running", and it depends on nothing outside the standard library, so calling tick twice with the same context always gives the same answer and the whole thing can be tested in isolation with a hand-built context.

Every piece of the tree is a node, and every node answers one question when it is ticked: did I succeed, and is there a command to report? That answer is a small result holding a success flag and a command string, where an empty string means that there is no command. There are four kinds of node. A Condition node holds the name of a fact and succeeds only if the context contains that name with a value other than zero, so a missing name behaves exactly like a zero, and a Condition never carries a command. An Action node holds a command string, always succeeds, and carries its command no matter what the context says. A Sequence node holds an ordered list of children and ticks them from left to right. It stops and fails at the first child that fails, and if every child succeeds it succeeds too, carrying the last non-empty command produced by its children, which means that a Condition placed after an Action does not erase the Action's command. A Selector node also holds an ordered list of children and ticks them from left to right, but it stops and succeeds at the first child that succeeds, carrying that child's command, and it fails only if every child fails. In plain words, a Sequence means "all of these must hold, then do this", and a Selector means "try these options in order and use the first one that works".

The tree is not built from hand-made nodes that point at each other. Each Sequence and Selector owns a vector of child nodes held through unique pointers, so the objects sit inside one another in exactly the same order as the code that created them, and a Sequence written with two Conditions and an Action really is an object containing a vector of those three objects. The helper functions Condition, Action, Sequence and Selector exist only to make that nesting easy to write, and BehaviorTree owns the root node, so destroying the tree frees everything beneath it automatically. Because a node's tick function calls the tick functions of its children, evaluation is naturally recursive: the BehaviorTree asks the root, the root asks its children, and each answer travels back up the same path.

The door example from the course shows how this works in practice. The root is a Selector with five children: four Sequences and a final Action called WalkToDoor. Suppose the context says AtDoor is 0. The first Sequence begins with the Condition Passou, which is not in the context at all, so it fails and the Sequence fails without ticking its remaining children. The Selector moves on to the second Sequence, whose first Condition AtDoor is 0 and fails, and the same happens with the third and fourth. The last child is an Action, which always succeeds, so the Selector succeeds with the command "WalkToDoor" and the BehaviorTree returns that string. Now suppose AtDoor is 1 and LockedDoor is 1. The first Sequence fails at Passou, the second passes AtDoor but fails at OpenedDoor, the third passes AtDoor but fails at UnlockedDoor, and the fourth passes AtDoor, passes LockedDoor and reaches the Action "unlock", which becomes the answer. Because children are tried in order, the order of the branches is also their priority: if Passou and OpenedDoor are both true, the first branch wins and the answer is "close" even if the character is also at the door.

A few behaviors are worth knowing because the implementation settles them explicitly. A failed result never carries a command, so when a Sequence fails after one of its Actions has already succeeded, that Action's command is thrown away and cannot leak into the Selector above it. Evaluation stops as soon as the outcome is known, so children after a failing Sequence child or after a succeeding Selector child are never ticked. A Sequence with no children succeeds with no command, because nothing in it can fail, and a Selector with no children fails, because nothing in it can succeed. If the same fact name appears more than once in the context, a Condition on that name holds when any of those entries is non-zero. A missing child inside a Selector or Sequence is treated as a node that always fails instead of being dereferenced, and a BehaviorTree built without a root simply returns an empty string. Finally, the public tick of BehaviorTree returns the command carried by the root's result, or an empty string when the root failed, and an empty string means that the character has no command this tick, not that something went wrong.

Two responsibilities remain with the caller. The first is to fill the context with fresh facts before each tick, since the tree only knows what the context tells it. The second is to spell the names consistently, because conditions are plain case-sensitive string lookups and the tree attaches no special meaning to any name: a misspelled condition does not raise an error, it just never succeeds. In the same way the command strings are just text, and it is the character's own code that turns "goThrough" or "unlock" into actual movement.
