# Documentation — PathFind.cpp Implementation

PathFind is a small class that answers one question for the game: given where a character is standing and where it wants to go, which sequence of tiles should it walk through so that the trip is as short as possible and never goes through a wall. It is declared in PathFind.hpp, implemented in PathFind.cpp, and uses the A* search algorithm. The class stores only three things: a pointer to the tile matrix, the width of the matrix and its height. The matrix is not copied. PathFind simply looks at it, so the matrix has to stay alive for as long as the PathFind object is used, and if the map changes later, for example when a door turns into a wall, the next call already sees the change because the matrix is read again every time. The matrix is the same kind that TileMap keeps: one integer per cell, stored row by row, so the cell at column c and row r sits at position row times width plus c. A cell is walkable only when its value is EMPTY_TILE, which is 0. Any other value, such as WALL_TILE, blocks movement, and every position outside the matrix counts as blocked as well. In normal use the object is built once from the TileMap, with its data pointer, its width and its height, and then findPath is called whenever a character needs a route.

findPath works with two coordinate systems. The caller speaks in world coordinates, which are continuous pixel positions where the y axis grows downward and every tile is TILE_SIZE pixels wide, 64 by default, while the search itself works on whole cells. The conversion follows the convention written in Global.hpp: the column is the floor of x divided by TILE_SIZE and the row is the floor of y divided by TILE_SIZE. A point that lies exactly on the border between two cells belongs to the cell on the right or below, and the right and bottom edges of the whole map, where x equals width times TILE_SIZE or y equals height times TILE_SIZE, are already outside the map. The test that the cell is inside the matrix is made on the floating point value before it is converted to an integer, so NaN, infinity and absurdly large values are rejected safely instead of triggering an undefined conversion. On the way out, every cell of the route is converted back to the world position of its centre, which is the column plus 0.5 times TILE_SIZE horizontally and the row plus 0.5 times TILE_SIZE vertically, the same formula TileMap uses in toWorld. This means the returned way points are exact cell centres and not the original start and goal positions the caller passed in.

The search treats the map as a graph in which every walkable cell is a node that can be connected to up to eight neighbours, four orthogonal and four diagonal. An orthogonal step costs 1 and a diagonal step costs the square root of 2, about 1.414, which is its real geometric length when tiles are squares, so the algorithm prefers one diagonal step over two orthogonal steps covering the same displacement, as a real walker would. Diagonal moves follow an extra rule from the contract that stops a path from clipping the corner of a wall: a diagonal step is allowed only if the destination cell is walkable and both cells that touch the diagonal orthogonally are walkable too. For example, to go from a cell to the one down and to the right, both the cell on its right and the cell below it must be free. If only one of them is a wall, the character has to go around with two orthogonal steps, and if both are walls, two floor cells that touch only at a corner are not connected at all.

A* explores the map in order of how promising each cell looks. For every cell it keeps g, the cheapest cost found so far from the start to that cell, and h, an estimate of the cost still missing to reach the goal, and their sum f is the estimated total cost of a route that passes through the cell. The open list holds the cells that have been discovered but not yet expanded, and the next cell to be expanded is always the one with the smallest f. Expanding a cell means looking at each allowed neighbour and computing what it would cost to reach that neighbour through the current cell. If that is cheaper than anything known before, the neighbour's g is updated, the current cell is remembered as the neighbour's parent, and the neighbour is placed in the open list. Cells that were already expanded are marked as closed and are not processed again. When the goal itself is taken from the open list the search stops, and the route is rebuilt by following the parent links from the goal back to the start and then reversing the order, so that it runs from start to goal. If the open list becomes empty before the goal is reached, the goal cannot be reached and the result is an empty list.

The estimate h is the octile distance. If dx and dy are the differences in columns and rows between a cell and the goal, the estimate assumes the character moves diagonally as much as possible, which is the smaller of dx and dy steps, and then straight for the remaining distance, so it equals the square root of 2 times the smaller difference plus the larger difference minus the smaller one. This is exactly the cost of the best route on a map with no walls, so it never overestimates the real cost, which is called being admissible, and it never drops by more than the cost of a single step, which is called being consistent. Those two properties together guarantee that the first time the goal is taken from the open list the route found is a shortest one, up to tiny floating point rounding, and that no cell ever needs to be expanded twice. A cruder estimate such as the Manhattan distance would overestimate diagonal trips and could return routes that are longer than necessary, while an estimate of zero turns A* into Dijkstra's algorithm, which is still correct but explores far more cells.

Some implementation details are worth knowing. The open list is a priority queue of small records holding f, h and the cell index. A cell may be pushed more than once when a cheaper route to it is found later, and the outdated copies are simply skipped when they come out of the queue because the cell is already marked as closed, which is simpler than a queue that can change priorities. Each call creates three arrays with one entry per cell: the g costs, initialised to infinity, the parent of each cell, initialised to a marker meaning none, and the closed flags. The eight possible moves are kept in a small constant table with the column offset, the row offset and the cost of each one. Ties are broken in a fixed order, lower f first, then lower h, then lower cell index, so the same query on the same map always returns exactly the same path. When several different routes are equally short, one of them is returned, and the choice is stable but the contract does not say which one.

findPath handles the special cases in this order. If the object was built with a null matrix or a non-positive size, which the constructor forbids with asserts and can only happen when asserts are disabled, the result is empty instead of reading bad memory. If the start or the goal falls outside the map, the result is empty. If the cell of the start or of the goal is not walkable, the result is empty. If both positions fall in the same cell, the result is a single way point, the centre of that cell. Otherwise the search runs, and when the goal is unreachable the function gives up with an empty list after having explored everything that can be reached from the start. The route always begins with the centre of the start cell and ends with the centre of the goal cell, and it contains every cell along the way, with no smoothing and no merging of straight segments, so a trip across n cells returns n way points. How to follow the route is up to the caller, who will typically steer the character toward the next way point and switch to the following one when it is close enough, and a character that is already standing in the first cell can skip that first point.

About cost, if N is the number of cells, the running time is at most proportional to N times the logarithm of N, which happens when the goal is unreachable or very far and almost every reachable cell gets expanded, and the memory used during one call is about 17 bytes per cell for the three arrays plus the open list, all of it allocated and released inside the call. On a 500 by 500 map, which has 250,000 cells, a corner to corner route on an empty map took about 2 to 5 milliseconds in the tests, and a query whose goal is behind a complete wall, where half of the map has to be explored before giving up, took about 44 to 150 milliseconds depending on the build. The function is const and keeps no state between calls, so it can be called repeatedly, and from several threads at once, as long as nobody modifies the matrix while the calls are running. If many characters ask for routes on very large maps, the first improvements to consider are reusing the arrays between calls and caching routes that are asked for often.

The implementation was checked in several ways. Its results were compared with an independent Dijkstra search on 4,000 random grids of different sizes and densities of walls, requiring the same total cost, or an empty result when no route exists, and requiring every way point to be the centre of a walkable cell and every step to obey the corner rule. It was also used to connect rooms in 40 dungeons produced by Dungeon2D, using the corrected version of the generator from the earlier review and loaded through TileMap, which gave 4,338 routes that were all valid and shortest, and whose way points agree with the cell conversion of TileMap itself. Specific cases were tested as well, such as the corner rule, starts and goals on walls or outside the map, positions that are NaN or infinite, unreachable goals, maps that are not square, and identical start and goal. Everything was run with address and undefined behaviour sanitizers, and eight deliberately broken versions of the code, with the corner rule removed, a wrong heuristic, rows and columns swapped, and similar mistakes, were each detected by the tests.
